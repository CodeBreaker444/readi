A **DCC** (Drone Control Center) is a client's external system that requests missions from Readi. Readi keeps it informed as missions progress. Each client has its own **integration**: its own addresses, its own choice of missions, and its own API key.

---

## Setup

Go to **Settings → Integrations → Client Integrations** (Admin and above). Select a **client** and set:

| Field | Notes |
|---|---|
| Client | Required. Pick from the client list. A client that already has an integration is marked **Configured** and loads its current values for editing |
| Missions to send | **All missions**, **External requests** or **Internal missions** (see below) |
| Callback URL | The client's server. Readi calls the DCC paths listed in the **Status Endpoints** table on it. It must not contain a query string (`?...`) or `#fragment`, because the paths are added after it |
| Status URL | Optional. Receives the simple mission status message described in [Client status URLs](#client-status-urls) |

Enter at least one of the two URLs and click **Add / Update**. Saving, rotating a key and removing are recorded in the [Audit Logs](/docs/records/audit-logs).

The list above the form shows every client with its integration: the missions it receives, its addresses and the last 6 characters of its key. From there you can **edit**, **rotate the key** or **remove** an integration.

<Warning>
There is no organisation-wide server any more. A client without an integration receives nothing, and an update is never sent to another client's server. Integrations created earlier keep working; they are set to **All missions** and have no key until you rotate one.
</Warning>

---

## Which missions are sent

| Option | The client receives updates for |
|---|---|
| **External requests** | Only missions the client requested itself through its API key (they appear under **Flight Requests → External**) |
| **Internal missions** | Only missions created inside Readi for that client |
| **All missions** | Both. This is the default |

If a mission does not match the integration's choice, the update is skipped (it is not an error and is not retried).

---

## API key

Every integration has its own API key, used by Readi to identify itself to the client's server, the same idea as the secret of an event-logbook webhook.

- A key is generated automatically when the integration is first saved. It is shown **once**: copy it and give it to the client.
- Afterwards only the **last 6 characters** are shown (for example `••••a3f9c1`) so keys can be told apart. The key is stored encrypted.
- Use **Rotate key** to replace it. The old key stops being sent immediately, so share the new one with the client first. Updates the client rejects meanwhile (401/403) are retried automatically.

Readi sends these headers with every call to the client's server:

| Header | Content |
|---|---|
| `X-API-Key` | The integration's key. The client's server should reject calls without the right one |
| `X-Readi-Timestamp` | Unix time of the call |
| `X-Readi-Signature` | `sha256=` + HMAC-SHA256 of `timestamp.body`, using the key as secret, so the client can verify the body was not altered |

An integration without a key (created before keys existed) still uses the old shared login until a key is rotated.

## Multiple clients

Several clients can request flights through the same Readi organisation, each with its own API key and integration.

1. **Settings → Security → API Keys**: create a key and pick its **Client**. A key with no client is organisation-wide (the original behaviour).
2. **Settings → Integrations → Client Integrations**: pick the same client and set its **Callback URL** and the missions to send.

A request is tied to the client of the key that sent it, and stays tied to it even if the key is later revoked or deleted. Accept, deny, started, finished and flight-log updates go to **that client's callback URL**. If the client has no integration, the update is skipped.

Mission IDs only need to be unique per client, and a client's key can only see and cancel that client's own requests.

---

## Drone mapping

The DCC identifies drones with its own ID. Enter it as **DCC Drone ID** (a long code provided by the DCC) on the system's **drone component**. If several active drones have one, the most recently installed is used.

<Warning>
Without a DCC Drone ID, the "Accepted" update is **not sent** to the DCC.
</Warning>

---

## Flow

1. The DCC creates a request, which appears under **Flight Requests → External**.
2. Readi checks the waypoint against the operation zones of the client's systems. If it is outside the zones of every system, the request is **rejected automatically**: Readi sends *Denied* with the reason, and the API response returns `"dcc_status": "REJECTED"` and a `reason`. Waypoint coordinates must be in GeoJSON order `[longitude, latitude, altitude?]`, with latitude between -90 and 90 and longitude between -180 and 180. Anything else is refused with `400 Validation failed`.
3. An OPM acknowledges the request, then **links it to a mission** (accepts) or **denies** it.
4. Readi informs the DCC at each step of the linked mission (below). The steps follow the mission's status on the Daily Board.

Missions created directly in Readi are also reported to the client's DCC when its integration includes **Internal** missions: **New mission** and **Cancelled**, and also **Started** and **Finished** (a mission that is aborted is reported as a failed finish, with the reason as the note). The mission code is used as the mission ID, the same one sent in the New mission update.

For missions requested by the DCC, Started and Finished come from the Flight Requests flow instead, so they are not repeated from the Daily Board.

## Updates sent by Readi

All updates are `POST` requests to the client's **Callback URL**, with the same paths and bodies as before.

| Update | Sent when |
|---|---|
| New mission | A scheduled or on-demand mission is created in Readi |
| Accepted | The request is linked to a mission (includes the drone of the mission's system) |
| Denied | An OPM denies the request, or it is rejected automatically because its location is outside the client's operation zones |
| Started | The linked mission is started on the **Daily Board** (internal missions: the same) |
| Finished | The linked mission is completed (success) or aborted / cancelled (failure, with the abort reason as the note) |
| Cancelled | A scheduled program is cancelled |
| Flight log | A flight log is pushed from the Flight Requests page |

The settings page also lists the exact addresses called, in the **Status Endpoints** table. It is collapsed by default: click its header to open it and share it with your DCC provider.

## Client status URLs

Besides the DCC paths above, a client's integration can have a **Status URL**. Readi sends the status of that client's missions to it, including missions created in Readi that never came from an external request. The **Missions to send** choice applies here too.

A status update is sent when:

| Event | Status sent |
|---|---|
| Mission started on the Daily Board | `IN_PROGRESS` |
| Mission finished (or reverted) on the Daily Board | `COMPLETED` (or `IN_PROGRESS`) |
| Status changed from the Operations table | The new status |
| A mission is aborted | `ABORTED`, with the abort reason as the note |
| A planned mission's day passes without it starting | `ABORTED`, with an automatic reason |

When you set missions to **Aborted** from the Operations table, Readi asks for an optional reason. It is saved on the mission and sent as the `note`.

Each update is a `POST` with a JSON body:

```json
{
  "missionId": "external id, or the mission code",
  "missionCode": "OP-1042",
  "missionName": "Bridge inspection",
  "status": "ABORTED",
  "note": "Wind above limits",
  "scheduledStart": "2026-11-19T08:00:00.000Z",
  "actualStart": null,
  "actualEnd": null,
  "sentAt": "2026-11-19T09:12:30.000Z"
}
```

A failed status delivery is logged and never blocks the action in Readi.

## Pushing a flight log

On a request, archive a Control Center flight, then use **Push to DCC**. It is sent as the mission's flight report. Manual logs cannot be pushed, and the mission needs a drone with a DCC Drone ID.

---

## Errors

A failed update never blocks the action in Readi. The failure is shown in a **DCC Error Details** message, which has a bug-report option.

### Retries and resend

Updates the DCC could not take are kept and retried automatically (every 5 minutes, backing off 1 min → 5 min → 30 min → 2 h → 6 h; 6 attempts in total). Only temporary failures are retried: network errors, timeouts, HTTP 401, 403, 408, 429 and 5xx. Any other 4xx answer means the DCC refused the update, so it is not retried. 401 and 403 are retried so that updates sent right after a key rotation still arrive once the client has the new key.

Anything still waiting or given up on is listed under **Settings → Integrations → Undelivered callbacks**, where an admin can **Resend** it at once. The list scrolls when there are many entries. The DCC should treat repeated deliveries of the same update as harmless, since a retry can arrive after a timeout the DCC actually processed. Cancellation updates are never retried: if the DCC rejects one, the cancellation in Readi is stopped instead.

A resend and every retry use the integration's current addresses and key, so fixing an address or rotating a key also fixes the waiting updates.

### Callback URL rules

In production a callback or status URL must use **https**, contain no username/password, and point to a **public** address. Localhost, private network, link-local and cloud-metadata addresses are rejected when saving and again before every send. Redirects are not followed.

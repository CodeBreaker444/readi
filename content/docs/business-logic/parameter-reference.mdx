## Cross-Module Parameter Dependencies

### Maintenance → Operations

| Maintenance Parameter | Operations Parameter | Dependency Logic |
|---|---|---|
| System Status (tool_status) | Drone Assignment (fk_tool_id) | Only OPERATIONAL systems can be assigned to missions |
| Component Status (component_status) | Mission Status (status_name) | System must be OPERATIONAL for mission start |
| Maintenance Hours (initial_maintenance_hours) | Flight Duration (flight_duration) | Mission duration updates component hours |
| Maintenance Flights (initial_maintenance_flights) | Mission Completion | Each mission increments component flights (multiplied by battery_cycle_ratio) |
| Open Maintenance Ticket | Mission Start | Open tickets prevent mission start (system in MAINTENANCE status) |

### Operations → Maintenance

| Operations Parameter | Maintenance Parameter | Dependency Logic |
|---|---|---|
| Actual End (actual_end) | Maintenance Hours (initial_maintenance_hours) | Mission completion triggers maintenance cycle update |
| Flight Duration (flight_duration) | Maintenance Hours (initial_maintenance_hours) | Flight duration added to component hours |
| Drone Assignment (fk_tool_id) | Maintenance Ticket System (fk_tool_id) | Missions linked to systems can have maintenance tickets |
| Mission Completion | Component Status | Recalculates OK/ALERT/DUE status based on updated metrics |

## Parameter Validation Rules

### Common Validation Patterns

#### String Validation
- Trim whitespace before storage
- Convert to uppercase for codes (tool_code, mission_code, etc.)
- Reject empty strings for required fields
- Max length: 255 characters for most fields

#### Numeric Validation
- Must be >= 0 for counts and durations
- Must be > 0 for limits and ratios
- Decimal precision: 2 decimal places for hours
- Integer for counts and IDs

#### Date Validation
- Must be valid ISO 8601 format
- End date must be >= start date (where applicable)
- Future dates allowed for scheduling
- Past dates allowed for historical records

#### Enum Validation
- Status fields: restricted to defined enum values
- Type fields: restricted to defined enum values
- Active flags: 'Y' or 'N' only

#### JSON Validation
- Must be valid JSON object
- Nested objects validated recursively
- Arrays must contain valid elements
- Null allowed for optional fields

### Module-Specific Validation

#### Maintenance Module
- `maintenance_cycle_hour`: Only used if > 0
- `maintenance_cycle_flight`: Only used if > 0
- `maintenance_cycle_day`: Only used if > 0
- `battery_cycle_ratio`: Must be > 0, default 1.0
- `component_active`: Only 'Y' components evaluated

#### Operations Module
- `flight_duration`: Calculated from actual_start and actual_end
- `max_altitude`: > 120m triggers compliance flag
- `battery_charge_start/end`: Must be 0-100
- `status_name`: Must follow defined transitions

#### Email Module
- `daily_email_limit`: Must be > 0
- `notification_roles`: Must be valid user roles
- `notification_user_ids`: Must be valid user IDs
- `module_name`: Must be 'maintenance', 'operations', or 'planning'

#### Planning Module
- `planning_status`: Only 'NEW' can be deleted
- `evaluation_status`: Only 'NEW' can be deleted
- `planning_json`: Must contain valid tasks array

#### Integration Module
- `flytbase_api_token`: Must be valid JWT
- `flytbase_org_id`: Required with token
- `serial_number`: Case-insensitive matching
- Placeholder SNS: 'n/a', 'na', 'unknown', 'none', '-', 'null' filtered

## Parameter State Transitions

### Maintenance Status Transitions

```
OK → ALERT (at 80% of limit)
ALERT → DUE (at 100% of limit)
DUE → OK (after maintenance, counters reset)
OK → IN_MAINTENANCE (ticket created)
IN_MAINTENANCE → OK (ticket closed)
```

### Mission Status Transitions

```
PLANNED → IN_PROGRESS (pre-flight check OK, system OPERATIONAL)
IN_PROGRESS → COMPLETED (post-flight check OK)
IN_PROGRESS → FAILED (incident flags)
PLANNED → CANCELLED (user action)
```

### Planning Status Transitions

```
NEW → PROCESSING (review started)
PROCESSING → REQ_FEEDBACK (awaiting sign-off)
REQ_FEEDBACK → POSITIVE_RESULT (approved)
REQ_FEEDBACK → NEGATIVE_RESULT (rejected)
NEGATIVE_RESULT → PROCESSING (revision)
PROCESSING → TESTING (testing phase)
TESTING → POSITIVE_RESULT (testing passed)
TESTING → NEGATIVE_RESULT (testing failed)
```

### Evaluation Status Transitions

```
NEW → PROCESSING (assessment started)
PROCESSING → DONE (assessment complete)
```

- Display names and descriptions
- Timestamp updates

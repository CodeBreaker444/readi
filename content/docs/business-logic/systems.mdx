A **System** in Readi is any physical asset tracked as a `tool` record in the database.

## System Fields

| Field | DB Column | Meaning |
|---|---|---|
| Asset code | `tool.tool_code` | Unique identifier (e.g. `DJI-M3T-001`) |
| Name | `tool.tool_name` | Display name |
| Active flag | `tool.tool_active` | `Y` = in service, `N` = decommissioned |
| Location | `tool.location` | Physical storage location |
| Activation date | `tool_metadata.activationDate` | When the asset entered service |
| Client assignment | `tool_metadata.clientId` | Which client this drone is dedicated to |
| Calibration | `tool.last_calibration_date` / `tool.next_calibration_date` | Calibration tracking |
| Warranty | `tool.warranty_expiry` | Warranty end date |

Each system can have **components** (`tool_component`): motors, batteries, sensors — each tracked individually for usage hours and expiry.

---

## Operational Status

Computed live on every fleet load. **Not a stored field.**

```
NOT_OPERATIONAL  >  MAINTENANCE  >  OPERATIONAL
```

| Status | Trigger condition |
|---|---|
| `OPERATIONAL` | No open tickets, no expired components |
| `MAINTENANCE` | Open maintenance ticket (`ticket_status != CLOSED`) OR component with `component_status = MAINTENANCE` |
| `NOT_OPERATIONAL` | Active component (`component_active = Y`) has `expiration_date <= today` (or has reached a flight / flight-hour limit) |

<Warning>
A system can satisfy both MAINTENANCE and NOT_OPERATIONAL simultaneously. NOT_OPERATIONAL always wins the display.
</Warning>

See [System Status Rules](/docs/platform-rules/system-status-rules) for the full computation.

## Decommissioned

**Manual:** Admin sets `tool_active = N` via Settings → Systems.

**Automated:** Components decommission automatically when they expire, that is, when they pass their expiry date or reach their flight or flight-hour limit. An expired component shows as Decommissioned and the system becomes Not Operational. The platform also sends expiration notifications to managers.

<Warning>
**Expiry is permanent by default.** An expired component cannot be made operational again and cannot be put on a maintenance ticket by hand (a ticket is still opened for it automatically, see below). To make the system operational, set the component to Decommissioned, remove it from the system, or move it to the warehouse.
</Warning>

### Renewable expiry (`expiry_permanent = false`)

The **Permanent expiry** checkbox on a component is stored as `tool_component.component_metadata.expiry_permanent`. A missing value means `true`, so every component created before the option existed is permanent.

| | `expiry_permanent = true` (default) | `expiry_permanent = false` |
|---|---|---|
| Effective status when expired | `DECOMMISSIONED` | `NOT_OPERATIONAL` (an explicit stored `MAINTENANCE`, `DECOMMISSIONED` or `DISMISSED` is kept) |
| System status | `NOT_OPERATIONAL` | `NOT_OPERATIONAL` |
| Maintenance ticket | Opened automatically, one per expiry (cannot be added by hand) | Opened automatically, one per expiry |
| Renewing the limits | Refused | Allowed. The component returns to its stored status |
| Changing the flag while expired | Refused | Refused |

When a renewable component expires it becomes `NOT_OPERATIONAL` and stays that way until its limits are renewed or it is set to `DECOMMISSIONED`. A maintenance ticket is opened for it automatically:

- The ticket has `ticket_type = STANDARD`, `ticket_priority = HIGH`, `reported_by_user_id = NULL`, and is linked to the component through `maintenance_ticket_item`.
- It is opened by the `check-component-expiration` cron (every 6 hours, for every expiry type), straight after a component is added or edited with an expired limit, and straight after a mission or flight sync raises a flight or flight-hour counter to its limit.
- The same applies to **permanent** expiry (`expiry_permanent = true` or missing): a ticket is opened for the system with a note that the component is Decommissioned (expiry is permanent), and the system shows `MAINTENANCE`. The component stays decommissioned and is not added to tickets by hand. A permanent component already stored as `DECOMMISSIONED` (taken out of the system) gets no ticket.
- It is skipped for decommissioned, dismissed, detached (warehouse) and inactive components, and when an open ticket already covers the component or the whole system. A component added to a system whose open ticket does not list it gets its own ticket.
- To avoid duplicates, the component stores `expiry_ticket_key` (the expiry limits plus `last_maintenance_date`) in its metadata, and its row is locked while the ticket is created. Renewing the limits, or performing maintenance, starts a new expiry and allows a new ticket. Closing a ticket on a component that is still expired records the key, so no second ticket is opened for the same expiry.
- The system's stored status is set to `MAINTENANCE` (see below), so it does not show `NOT_OPERATIONAL` while the ticket is open.

A user can also put it on a maintenance ticket: an expired renewable component is ticketable even though its status is `NOT_OPERATIONAL`. A component with a stored `NOT_OPERATIONAL` (for example from a reported issue), `DECOMMISSIONED` or `DISMISSED` status, or a detached one, is still not ticketable. Closing the ticket resets the component's counters but does not renew an expired date, so renew or decommission it separately.

When a ticket is created (by a user, or automatically for an expired component) for a system whose stored status is `OPERATIONAL` (or empty) but that is `NOT_OPERATIONAL` because of an expired component, the system's stored status is set to `MAINTENANCE`, so the fleet list shows Maintenance. This applies to permanent and renewable expiry. It is set back to `OPERATIONAL` when the last open ticket closes; if an expired component is still in the system, the computed `NOT_OPERATIONAL` shows again. A status set by hand (`NOT_OPERATIONAL`, `DISMISSED`, ...) is never overwritten.

| State | `tool_active` | In fleet? | Missions? |
|---|---|---|---|
| In service | `Y` | Yes | Yes |
| Decommissioned | `N` | No | No |
| Soft-deleted | `Y` but `tool_metadata.deleted = true` | No | No |
| Warehouse | `Y` but `tool_metadata.is_warehouse = true` | No | No |

A **system** is a drone and everything it is built from. Each part (the drone itself, a battery, a motor, a controller) is a **component** with its own serial number and usage. Open **Systems** in the sidebar to manage them. This page covers the tools beyond adding and editing records.

---

## Systems map

**Systems → Map** (Drone System Map) shows your installed docks and drone systems on a map.

- **Filters:** by **Status** (Operational, Not Operational, Maintenance, Decommissioned), by **Client**, and a search box (for example a system code). **Docks only** and **Installed only** narrow it further.
- **Legend:** the symbols are the Control Center, Dock, Drone and Cluster (several systems close together), coloured by status.
- **Tool List:** a table of the systems on the map. **Locate** jumps to one on the map, and **Detail** opens its details: general info, specifications and its components.
- **Panel tabs:** **Systems** shows the components attached to a system, and **Warehouse** shows the spare components that are not on any system, with their serial numbers.
- A system with no location is not shown on the map ("No map location available for this item").
- **Reload** refreshes the map.

---

## Location name

A system can have a **Location Name** next to its map coordinates, for example "Warehouse A". It makes lists, exports and the Maintenance Logbook easier to read than raw coordinates. Missions have one too (see [Operations](/docs/modules/operations)).

## Operation zones

A system can have **operation zones**: an optional overlay that says where it may fly. They are shown on the map and checked against every flight request from the system's client. You can set them when you add a system or later.

| Zone | Colour | Meaning |
|---|---|---|
| **Green zone** | Green | Safe and approved to fly |
| **Red zone** | Red | Restricted, do not fly (for example a substation or a power line) |
| **Unsurveyed zone** | Grey | Not checked yet, fly only after a survey |
| **Perimeter** | Blue dashed line | The operational limit of this system. A system has one perimeter |

Zones can be **polygons** (areas), **lines** (for example a power line) or **pins** (a single point, for example a mast). A red line or red pin blocks anything within about 30 m of it. Every zone has a name you can edit.

### Add or edit zones

- **When adding a system:** open the **Operation zones (optional)** tab. Everything on it is optional, and the tab shows how many zones you have drawn.
- **On an existing system:** in **Systems → Manage**, click the fence icon on the system row (tooltip **Operation zones**), then **Save zones**. Users who can only view systems see the zones but not the Save button.

The map opens in **satellite** view. The layers button switches to the street map.

| Tool | What it does |
|---|---|
| Polygon | Click the map to place the corners of an area, then press **Enter** or the tick button |
| Line | Same, for a line zone |
| Pin | Click the map once to place a pin |
| Fence | Draws the operational perimeter. Drawing a new one replaces the old one (a message tells you). **Esc** keeps the old one |
| Green, red, grey dots | The type of the next zone you draw. With a zone selected, they change its type |
| Undo, tick, cross | Remove the last point, finish the shape, cancel it (**Esc**) |
| Zoom to all zones | Fits the map to everything you drew |

Click a zone on the map or in the list to select it. Drag its points to reshape it, or right-click a point to remove it. Use the list under the map to rename a zone, change its type or delete it.

### Import a KMZ or KML file

Click **Import KMZ** and choose a `.kmz` or `.kml` file, for example one exported from Google Earth. Every polygon, line and pin in it is added as a zone. A KMZ is a zipped KML.

The type of each shape is decided in this order:

1. **Custom fields in the file:** fields that an external service added to a shape (KML `ExtendedData` or `SimpleData`) named *type*, *zone*, *category*, *class*, *status*, *restriction*, *level*, *risk*, *kind* or *color*. A value such as *restricted*, *no-fly*, *approved* or a colour like `#00cc00` decides the type.
2. **Its name** (or a *name*, *title* or *label* field when the shape has no name): words such as *red*, *no-fly*, *restricted* make it red. *green*, *safe*, *approved* make it green. *unsurveyed*, *unknown*, *grey* make it grey. *perimeter*, *boundary*, *fence* make it the perimeter.
3. **Its colour** in the file (the fill, line or pin colour: green, red or grey).
4. **Its description**, when it is short, using the same words.
5. **The name of its folder**, using the same words.
6. If nothing matches, it is imported as **unsurveyed** (grey). Check and change it in the list.

Pins without a name or colour that points to a type are added as unsurveyed. **DJI wayline files** (a KMZ made in DJI Pilot or FlightHub) are imported as one pin per waypoint, named "Waypoint 1", "Waypoint 2" and so on, exactly as Google Earth shows them. Image overlays and empty shapes are skipped, and the message tells you how many. After the import, a message shows how many areas, lines and pins were added.

Other information in the file is kept as a **note** on the zone: the altitude and speed of a DJI waypoint, and any other custom fields. Hover over the zone on the map, or over its name in the list, to read it. Tracks (`gx:Track`) are imported as lines, and a DJI archive that only contains `waylines.wpml` also works. If the file has several perimeters, only the first is used. Importing into a system that already has zones adds to them. Holes inside polygons are ignored. After importing, review the list and **Save zones**.

### Limits and things to know

- **Size:** up to **500 zones**, **5,000 points** per shape and **100,000 points** in total per system. A KMZ/KML file can be up to **10 MB**. When you import a shape with more than 5,000 points, Readi keeps evenly spaced points so the shape stays close to the original.
- **Holes are ignored.** A polygon with an inner ring (for example a green area with a building cut out) is imported as a solid area. Draw the hole as a separate red zone.
- **Crossing outlines:** if a shape crosses itself, the crossed part counts as outside it. Redraw it without crossings.
- **Dateline:** shapes that cross the 180° meridian are not supported.
- **Red lines and red pins** block about 30 m around them. **Unsurveyed** lines and pins warn within the same distance. **Green** lines and pins are shown on the map but are not checked.
- **Duplicate:** **Duplicate system** copies the zones to the new system.
- **One perimeter per system.** To cover several sites, use green zones for each, or create one system per site.
- **Warnings are advice.** They never block a request, and the warning text on the flight request is in English.

### Warnings on flight requests

When an OPM opens an **external** flight request that has a waypoint, Readi checks the waypoint against the zones of every system assigned to that client. The result shows at the top of the request (Details and Action tabs), and the **Location** tab draws the zones and perimeter around the waypoint.

| Result | Shown as |
|---|---|
| Inside a green zone, inside the perimeter | Green: within its operation zones |
| Inside a red zone, or near a red line | **Red** danger warning |
| Inside an unsurveyed zone | Amber warning |
| Outside the perimeter | Amber warning |
| Inside the perimeter but in no green zone | Amber warning |

A warning does not block the request. It tells the OPM what to check before acknowledging or planning. Systems without zones, and clients whose systems have none, show nothing.

## Row buttons

In **Systems → Manage**, the buttons on each system and component row are icons. Hover over one to see its name. On a system row they are **View**, **Edit**, **Duplicate**, **Files**, **Relations**, **Operation zones** (fence icon) and **Delete**. On a component row they are **View**, **Edit**, **Log**, **Flights**, **QTB report** (drones only) and **Delete**. The ones you are not allowed to use are hidden.

## QTB report (PDF)

The QTB report is a printable flight record for a drone. It is available on **drone** components.

1. In the components list, find the drone and choose **QTB Report**.
2. Pick a **start date** and an **end date**. They use your own timezone, and both start as today.
3. Click **Generate PDF**. The file downloads straight away.

The end date must be on or after the start date. If you choose a very long period you may see "too many flights"; just narrow the dates and try again.

## Duplicate System

Use **Duplicate System** to set up a new drone that is like an existing one, without typing everything again.

1. Choose **Duplicate** on the system you want to copy.
2. **System Details** tab: the details are copied and the code ends in `-copy`. Change the **Code** and choose the **Client** (both are required). You can also change the description, location, status and activation date.
3. **Components** tab: every component of the original is copied as a new one, and you can review them one by one. Codes and serial numbers also end in `-copy`, so replace them with the real ones. You can edit the type, name, model, dates, vendor, maintenance cycle and parent component of each.
4. Click **Save Duplicate**.

The copy is a brand-new system with its own components. The original is not changed.

## Component relations

**Relations** lets you organise the parts of a system into a simple family tree, for example a battery and a camera that belong to a drone.

- Open **Relations** on a system. Every component has a **Parent** dropdown.
- Choose a parent to make a component a **child** of another. Choose **None (top-level)** to take it out again.
- **Live Preview** shows the result before you save. Click **Save** to apply it.

There is only **one level**:

- A component cannot be its own parent.
- Only top-level components can be parents. A child cannot have children of its own.
- A component that already has children cannot become a child. Remove its children first.

### Primary component

In the same window, choose the **Primary Component** of the system, normally the drone itself. It is marked **PRIMARY** and is the component shown for the system in mission details. Only one component can be primary at a time.

## Warehouse: moving and reassigning components

Spare parts that are not on a drone live in the **Warehouse**.

- To take a component off a system, **detach** it and confirm. It moves to the warehouse. A component that is still attached to a system cannot be deleted, so detach it first.
- The **Warehouse** tab, in the components list and on the systems map, shows what is available, with serial numbers.
- To use a warehouse component again, assign it to a system. This is how you swap a battery or move a part from one drone to another.

Components in the warehouse are not offered as systems for missions. Detaching is recorded as a secure transaction in the [Audit Logs](/docs/records/audit-logs).

## Component Log and Flights

Each component has two views of its own history:

| View | Shows |
|---|---|
| **Log** | A timeline for this component, such as location changes and the missions it was used on |
| **Flights** | The flight logs for this component |

Use them to answer "how much has this battery been used?" or "where has this part been?".

## Component statuses

A component has one of five statuses:

| Status | Meaning |
|---|---|
| **Operational** | In service and usable |
| **Not Operational** | Not usable at the moment |
| **Maintenance** | Being serviced. Holds the system in maintenance |
| **Dismissed** | Retired administratively |
| **Decommissioned** | Permanently out of service. The system no longer counts it |

### Permanent expiry option

When you add or edit a component, the **Permanent expiry** checkbox sits under the expiry fields. It is **checked by default**. It decides what happens when the component expires, that is, when it passes its expiry date or reaches its flight or flight-hour limit.

| | Permanent expiry (checked) | Not permanent (unchecked) |
|---|---|---|
| Status on expiry | **Decommissioned** | **Not Operational** |
| Maintenance ticket | Cannot be created | Created by a user (never automatic) |
| Can it be made Operational again? | No | Yes, by creating a ticket for it and closing it (its expiry is renewed) |
| How the system becomes Operational again | Only when the component is **removed from the system** (removed or moved to the warehouse) | Close the ticket (expiry renewed), or set the component to **Decommissioned** |

The checkbox is locked while the component is expired, so an expired component cannot be switched from one mode to the other.

### Expiry that can be renewed (checkbox unchecked)

When the component expires:

- It shows as **Not Operational** and the system becomes **Not Operational**.
- **No ticket is created automatically.** A user creates the maintenance ticket: the expired component can be selected like any other component (for the component or for the whole system). A component that is Not Operational for any other reason, or that is Decommissioned or Dismissed, cannot be selected.
- **When the ticket is created, the system shows Maintenance.** If the system was Not Operational only because of the expired component, it switches to **Maintenance** instead of staying Not Operational. A status you set by hand on the system is never changed.

**Its expiry cannot be edited while it is expired.** If you change the expiry date, the flight limit or the flight-hour limit of an expired component and save, you get an error: it can only be done by creating a maintenance ticket and closing it.

To get it working again, choose one:

- **Make it operational:** create a maintenance ticket for the component (or for the whole system) and close it. **Closing the ticket renews the expiry automatically:**

  | Expiry type | New value |
  |---|---|
  | Expiry date | **1 month** after the later of the old expiry date and today |
  | Flights | the flight limit **+ 10** |
  | Flight hours | the flight-hour limit **+ 10** (counted from the hours flown if that is higher) |
  | Mixed | only the limits that were reached are renewed |

  The **Close Ticket** window shows the new values before you confirm. The component becomes Operational again and the ticket timeline records the renewal.
- **Change the new value:** once the component is no longer expired, you can edit its expiry like any other component.
- **Decommission it:** set its status to **Decommissioned**. The system no longer counts it.

### Expiry is permanent (checkbox checked, default)

When a component passes its expiry date, or reaches its flight or flight-hour limit, it is **expired**, and expired is final:

- It shows as **Decommissioned** and the system becomes **Not Operational**.
- **It cannot be made Operational again.** Extending its expiry date or limits, or changing its status, is refused.
- **It cannot be put on a maintenance ticket.** Expiry means the component is retired for good, not waiting for service.
- **The system stays Not Operational until the component is removed from it.** Setting its status to Decommissioned does not free the system.

<Note>
**Setting an expiry date of today or in the past** makes the component read as Decommissioned and its system **Not Operational**. The Status field in the Edit Component dialog shows the status that is saved, and it is only changed if you change it, so saving an expiry date does not decommission the component by itself. It does not free the system either: the system stays Not Operational until the component is removed from it.
</Note>

To make the system operational again, **remove the expired component from the system**, in one of these ways:

- Remove it from the system.
- Move it to the warehouse.

Then fit a replacement component if the system needs one.

## Models, component types and drone classes

Drop-down lists such as the model, type and class of a component are managed by you, from the system screens.

- **Models:** use **Add Model** to describe a drone or other equipment once and reuse it. A model holds the brand, model code and name, type and sub-type (for example multirotor, fixed wing, VTOL or dock), weight, operating conditions (wind and temperature range), performance (endurance, speed, altitude), the maintenance cycle and the guarantee. Use **Edit Model** to change one later. The wind and temperature limits are the ones used for the weather forecast in [Operations](/docs/modules/operations).
- **Manage Component Types:** add, rename or remove the types you can choose for a component.
- **Manage Drone Classes:** add or rename the drone classes.

---

## Insurance and alerts

A component can store its **insurance** details: the insurance name, company and **expiry date**. To be warned before it expires:

- **Notify Users:** choose which users are emailed.
- **Days before:** how many days before expiry the reminder is sent.
- **Additional Emails:** add people who do not have a Readi account.

## New

### Client Integrations

In **Settings → Integrations**, the DCC server card and the Client mission status URLs card are merged into one **Client Integrations** section. Every integration belongs to one client and holds its callback URL, an optional status URL, the missions it receives and its API key.

- **Add, edit, remove:** pick a client, fill in the fields and click **Add / Update**. Picking a client that is already configured loads its current values. The list below the form shows every client with its scope, addresses and key. Removing an integration asks for confirmation first.
- **Pagination:** the list shows 8 integrations per page and adds page buttons when there are more.
- **No organisation-wide server any more.** A client without an integration receives nothing, and an update is never sent to another client's server. Check that every API key used by an external system is assigned to a client (**Settings → Security → API Keys**), because requests from a key with no client no longer get callbacks.
- Existing client URLs keep working. They are set to **All missions** and have no key until one is generated.

### Choose Which Missions Are Sent

A new **Missions to send** dropdown on each integration decides what the client receives:

| Option | The client receives updates for |
|---|---|
| **External requests** | Missions the client requested itself through its API key |
| **Internal missions** | Missions created inside Readi for that client |
| **All missions** | Both (default) |

Missions outside the choice are skipped. They are not an error and are not retried.

### Per-Client API Key

Every integration has its own API key, which Readi uses to identify itself to the client's server, like the secret of an event-logbook webhook.

- **Shown once.** The key is generated when the integration is first saved and shown with a copy button. After that only the **last 6 characters** are shown (for example `••••a3f9c1`). The key is stored encrypted.
- **Rotate key** replaces it. A confirmation window warns that the old key stops being sent immediately.
- **How it is sent:** every call carries an `X-API-Key` header, plus `X-Readi-Timestamp` and an `X-Readi-Signature` (HMAC-SHA256 of the timestamp and body, using the key), so the client can check who sent it and that the body was not changed.
- Integrations without a key keep using the previous shared login until a key is generated.
- Saving, rotating and removing an integration are written to the Audit Logs.

### Start and Finish for Internal Missions

Missions created in Readi now report **Started**, **Finished** and **Aborted** to the client's **callback URL**, in the same format used for external requests. Before, a client with only a callback URL heard about new and cancelled missions but never about start and finish.

| Event on the Daily Board | Sent to the callback URL |
|---|---|
| Mission started | `POST /dcc/missions/{code}/execution` |
| Mission finished | `POST /dcc/missions/{code}/termination` with `result: 1` |
| Mission aborted | `POST /dcc/missions/{code}/termination` with `result: 0` and the reason as `note` |

The mission code is used as the mission ID, the same one sent when the mission was created. The status URL still receives its simple status message. Missions requested by the DCC keep reporting through the Flight Requests flow and are not repeated from the Daily Board.

### Operation Zones for Systems

A system can now have **operation zones**, an optional overlay of where it may fly. There are **green** (safe), **red** (restricted) and **unsurveyed** (grey) zones, each with a name, plus one **operational perimeter**. Zones can be areas or lines.

- **Draw or import:** when adding a system, open the new **Operation zones (optional)** tab. The map opens in **satellite** view. Draw polygons and lines, or click **Import KMZ** to add every zone from a `.kmz` or `.kml` file at once. The type of each shape is taken from its name or colour, and anything unclear is added as unsurveyed. Pins are supported too, and DJI wayline KMZ files import as one pin per waypoint, as in Google Earth.
- **Existing systems:** in **Systems → Manage**, the new fence icon on a system row opens the same map. Change zones, then **Save zones**.
- **Warnings on flight requests:** when an OPM opens an external flight request, its waypoint is checked against the zones of the client's systems. A red banner shows a waypoint in a red zone or near a red line. An amber banner shows one outside the perimeter, in an unsurveyed zone or in no green zone. The **Location** tab draws the zones around the waypoint. A warning does not block the request.
- **Duplicate system** copies the zones to the new system.
- Limits: 500 zones, 5,000 points per shape and 100,000 in total per system, and KMZ/KML files up to 10 MB. Polygon holes are ignored.
- Saving zones is written to the Audit Logs. Systems without zones behave exactly as before.

### Pilots (PIC) on Flight Requests

A PIC can now work on **Flight Requests** when the role has access to it in the permission matrix (**Operation → Flight Requests**). **Pilots (PIC) get this access by default.**

- **Acknowledge, plan and fly:** a PIC with read and write access can **Acknowledge** an external request, **Move to Planning**, and set it **In Progress**, **Completed** or **Issue**. Read-only access shows the list without action buttons.
- **The matrix now decides.** The Flight Requests screens no longer also require the Planning permission, so ticking or clearing the feature for a role takes effect on the list, the actions and the log push.
- **Deny stays with OPM-level roles.** A PIC does not see the Deny button, and the server rejects it too.
- **The Internal tab stays with OPMs and admins.** A pilot's own missions that wait for approval are still followed on the Mission Table.

### Pilots Can Only Add Themselves to a Mission

A PIC who is not a manager can now only **add themselves** as the pilot of a PLANNED mission that has no pilot yet.

- A PIC cannot assign another pilot, and cannot change a mission's pilot once one is set. This applies to **Set pilot** on the Mission Table, editing a mission and creating a mission.
- In **Set pilot**, the list shows only the PIC, and missions that already have a pilot are skipped.
- The error message follows the language selected in the app (English, German and Italian).
- OPMs, admins and managers can still assign or change any pilot.

## Improvements

### Icon Buttons on Manage Systems

The buttons on each system and component row of **Systems → Manage** are now icons with a tooltip, so more of the table fits on screen.

### Collapsible Status Endpoints

The **Status Endpoints** table is collapsed by default. Click its header to open it and share the paths with your DCC provider.

### Scrollable Undelivered Callbacks

The **Undelivered callbacks** list now has a fixed height and scrolls, so many failures no longer stretch the page.

### Retries After a Key Change

Updates a client's server rejects with HTTP **401 or 403** are now retried automatically, like other temporary failures. Updates sent while a client still has the old key are delivered once it has the new one.

### Callback URL Check

A callback URL with a query string (`?…`) or a `#fragment` is rejected when saving, because Readi adds the DCC paths after the address. The message is shown in the notification. The status URL can still contain a query string.

### Documentation

The Flight Requests, Operations and Mission Approval pages describe what a pilot can do and the pilot assignment rule (in English and Italian). The DCC Integration page describes Client Integrations, the missions choice, the API key and headers, and the new retry rules. The Settings and Security and database tables pages are updated to match. The settings page is available in English, German and Italian. The Systems and Operations pages describe operation zones, KMZ import and the flight request warnings (in English and Italian).

## Fixes

### One Bad Callback Could Stop All Retries

If a stored key could not be read (for example after the server's encryption key changed), the retry job stopped for every client. That callback is now marked as skipped and the others are processed. A manual **Resend** on it shows a result instead of failing.

### Integration Without Any Address

An integration can no longer be saved with both URLs empty.
